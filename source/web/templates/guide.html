01개요

요약GitHub Security Advisories API에서 패키지 보안 취약점 공지를 수집하여 Notion에 저장하고, 서비스별 패키지 버전과 대조하여 취약도를 판정합니다. 결과는 Flask 웹 대시보드로 시각화하며, 작업 완료 및 오류 내역은 Slack으로 전송합니다.

01 · 수집

보안 공지 수집

GitHub Security Advisories API에서 지정 기간의 패키지 보안 취약점 공지를 수집합니다.

02 · 저장 · 판정

Notion 저장 · 취약도 판정

Notion DB에 중복 없이 저장하고, 서비스별 패키지 버전과 대조하여 취약도 판정 및 통계 집계를 수행합니다.

03 · 시각화

웹 대시보드

Flask와 HTML 기반 대시보드에서 요약, 공지 통계, 분석 결과, 취약 근거를 확인할 수 있습니다.

04 · 반영 · 알림

결과 반영 · Slack 알림

판정 결과는 Notion에 반영하고, 작업 완료 및 오류 내역은 Slack으로 전송합니다.

02도입 배경

요약보안 공지는 매일 신규 등록되고 기존 공지도 지속적으로 갱신됩니다. 공지 확인 · 대조 · 근거 관리를 수작업으로 처리하는 부담을 줄이기 위해 전 과정을 하나의 흐름으로 자동화했습니다.

수작업 처리 시 문제

  • 확인 — 신규 · 갱신 공지를 담당자가 매번 직접 확인해야 합니다.
  • 대조 — 공지의 취약 버전 범위와 서비스 패키지 버전을 건별로 비교해야 하며, 생태계마다 버전 규칙이 다릅니다.
  • 근거 관리 — 취약 판단 근거가 문서화되지 않고 분산됩니다.

시스템 적용 후

  • 자동 수집 — 지정 기간의 공지를 일괄 수집하고, 기존 공지는 제외 또는 갱신 처리합니다.
  • 자동 판정 — 패키지명 · 생태계 · 버전을 생태계별 규칙으로 대조하여 심각도를 저장합니다.
  • 근거 제공 — 취약 판정의 원인 공지와 버전 범위, 판정 불가 사유를 화면에서 확인할 수 있습니다.

03시스템 구성

요약시스템은 웹 대시보드 · 서비스 계층 · 외부 연동의 3계층으로 구성됩니다. 대시보드에서 작업을 요청하면 서비스 계층이 처리하고, 데이터는 Notion에 저장되며 결과와 오류는 Slack으로 전송됩니다.

  • 공통 연동 모듈 (source/common) — GitHub 수집(github_advisory), Notion 클라이언트 및 요청 간격 · 재시도 정책(notion), Slack 알림(slack)을 모듈 단위로 관리합니다.
  • 웹 계층 (source/web) — 화면 및 API 라우트, 조회 캐시, 수집 · 분석 작업의 진행 상태를 관리합니다. 장시간 작업은 백그라운드로 실행되어 화면 이동 시에도 중단되지 않습니다.

05처리 흐름

요약사용자 작업은 "신규 공지 가져오기"와 "분석 실행" 두 가지입니다. 전자는 수집 · 저장을, 후자는 판정 · 반영을 수행하며, 결과는 대시보드와 Slack에서 확인할 수 있습니다.

  1. 공지 수집이시원대시보드에서 기간(게시일 기준)을 지정하고 신규 공지 가져오기를 실행하면, GitHub에서 검토 완료된 공지를 수집합니다.advisories.py · get_advisories()
  2. 중복 확인 · 저장이시원 · 김기현공지 ID로 Notion을 조회하여 신규 공지는 저장하고, 기존 공지는 제외 또는 갱신합니다. 처리 결과는 Slack으로 전송됩니다.advisory_sync.py · sync_advisories_to_notion() / notion.py
  3. 취약도 분석노유성실행 상태 화면에서 분석을 실행하면, 저장된 전체 공지와 서비스 패키지를 대조하여 패키지별 취약도를 Notion에 반영합니다.processor.py · evaluate_impact() / version_comparison.py
  4. 시각화조성현대시보드 · 공지 분석 · 분석 결과 · 취약 근거 화면에서 Notion 데이터를 요약, 차트, 표 형태로 확인할 수 있습니다.source/web · advisory_analysis.py
  5. 알림엄동규적재 완료, 분석 완료, 오류 내역을 Slack 채널로 전송하여 대시보드 접속 없이도 처리 결과를 확인할 수 있습니다.source/common/slack

06주요 기능 ① 수집 · 중복 방지

요약GitHub Advisories api 를 연동해 데이터를 조회하며, 중복 방지 및 데이터 수정 등의 데이터 필터링을 진행합니다.

수집 조건

  • GitHub 게시일(UTC) 기준 기간(시작일 · 종료일 포함)으로 수집하며, 화면 기본값은 오늘을 포함한 최근 7일입니다.
  • 검토 완료(reviewed) 공지를 갱신일 내림차순으로 수집합니다.
  • 저장 항목: ID(GHSA), 제목, 링크, 게시일, 갱신일, 심각도, CVE, 생태계, 패키지명, 취약 버전 범위, 원인(CWE)

설계 기준

  • ID 기준 조회 — 수집한 ID를 기준으로 Notion data 를 조회 및 일치하는 ID 를 필터링하고, 조건에 따라 업데이트하여 primary key 가 없는 노션 db 를 보완했습니다.
  • 중복 행 정리 — ID와 저장일, 수정일을 활용한 삭제 기준을 통해 중복 행을 정리하여 데이터 무결성을 유지하고자 했습니다.
  • 재실행 안전성 — Notion은 롤백을 지원하지 않습니다. 처리 중 실패하더라도 동일 기간으로 재실행하면 저장된 공지는 제외되므로 결과의 일관성이 유지됩니다.
  • 조회 실패 시 저장 중단 — 중복 확인 없이 저장하면 대량 중복이 발생할 수 있으므로, 조회 실패 시 작업을 중단하고 오류를 전송합니다.
  • UTC 분 단위 비교 — GitHub(...Z)과 Notion(...+00:00)의 날짜 형식을 통일한 후 비교합니다.
구현 포인트 · GitHub API 연동 예외 처리 · 중복 방지 기준

GitHub API 연동 예외 처리

GitHub Advisories API 연동 시 예외 유형별로 로그를 세분화하여 오류 원인 추적의 편의성을 높였습니다.

예외 유형로그처리
HTTP 400 · 401 · 403 · 404Client Error재시도하지 않고 즉시 중단 — 토큰 · 요청 조건 등 연동 정보 확인이 필요한 오류
HTTP 5xxGithub Server Error재시도
그 외 HTTP 오류Unexpected Http Error재시도
연결 실패Github Server Connection Error재시도
응답 시간 초과 (5초)Github Server Timeout Error재시도
기타Unexpected Server Error재시도
  • 클라이언트 오류를 제외한 경우는 상대 서버가 일시적으로 연동 불가한 상황을 고려하여 재시도 로직을 적용했습니다. 재시도 횟수는 설정 파일(config.json의 max_retry, 기본 3회)로 관리합니다.
  • 재시도 반복문에 time.sleep(0.5)를 두어 요청 간 지연 시간을 부여함으로써, 장애 중인 서버에 요청이 연속으로 집중되지 않도록 했습니다.

중복 방지 기준

  • ID 일치 — Notion에 동일한 ID의 공지가 있으면 신규로 적재하지 않습니다.
  • ID 일치 · updated_at 상이 — GitHub에서 공지 내용이 변경된 것으로 간주하고, 기존 행을 최신 내용으로 업데이트합니다.
  • ID 일치 · published_at 상이 — 게시일은 GitHub Advisories에서 변경되지 않는 값입니다. 따라서 값이 다르면 Notion에서 임의로 수정되어 데이터 무결성이 훼손된 것으로 판단하고, GitHub 원본 값으로 복원합니다.

07주요 기능 ② Notion 모듈

요약Notion은 수집 데이터와 분석 결과를 모두 저장하는 공통 저장소입니다. Notion API 호출을 NotionClient 하나로 모듈화하여 수집 · 분석 · 화면 조회 기능이 동일한 방식으로 데이터를 조회 · 생성 · 수정 · 삭제하도록 구성했습니다.

제공 기능

메서드기능사용처
create_database()부모 페이지 하위에 DB(데이터 소스) 생성DB 초기 구성
create_database_row()행(Notion 페이지) 생성공지 신규 저장
get_database_rows()날짜 조건 조회, 페이지네이션 자동 처리, 컬럼 값을 Python 값으로 변환분석 · 화면 조회
update_database_rows()지정 컬럼 수정공지 갱신, 취약도 반영
delete_database_row()행을 휴지통으로 이동(복구 가능)중복 공지 정리
  • 컬럼 값 변환 — 제목 · 텍스트 · 선택 · 날짜 · 관계 등 Notion 속성 형식을 문자열 · 리스트로 변환하여, 호출부에서 일반 dict처럼 사용할 수 있습니다. 각 행에는 수정 · 삭제에 사용하는 실제 페이지 ID(page_id)를 함께 반환합니다.
  • 요청 정책 (query_policy.py) — 앱 전체 Notion 요청의 시작 간격을 0.5초 이상으로 유지하고, 429 · 5xx · 타임아웃은 Retry-After를 준수하여 최대 3회 재시도합니다.
  • 오류 알림 연계 — 모든 메서드에 @notify_errors를 적용하여 연결 · 조회 · 저장 실패 시 Slack 오류 알림이 전송됩니다.

데이터 구조

Notion DB는 보안 공지 · 서비스 · 서비스 패키지 3개로 구성되며, 컬럼 구조는 databases/schemas/에 정의되어 있습니다. 서비스 패키지는 서비스와 관계(relation)로 연결되고, 분석 결과는 서비스 패키지의 취약도(vulnerability) 컬럼에 저장됩니다.

DB주요 컬럼용도
보안 공지 (advisories)id · title · url · published_at · updated_at · severity · cve_id · ecosystem · package_name · package_version_range · reasonGitHub 수집 공지 (1행 = 공지 1건, 첫 번째 패키지 기준)
서비스 (service)id · resource_name · business_domain · description · business_importance운영 서비스 목록
서비스 패키지 (service_package)id · service_id(관계) · ecosystem · package_name · package_version · vulnerability서비스별 설치 패키지 및 분석 결과(safe · unknown · low ~ critical)

Notion 선정 사유: 비개발자도 결과를 즉시 조회 · 편집할 수 있고, 단기 프로젝트에서 별도 저장소 구축 부담이 없습니다. 고유키 제약이 없는 한계는 코드상의 중복 확인 로직으로 보완했습니다.

구현 포인트 · 매개변수 기본값을 활용한 기능 구성

매개변수에 기본값을 지정하여 Notion 기능을 연동했으며, 교육 과정에서 학습한 함수 매개변수 · 키워드 인자 활용 방식을 응용하여 구현했습니다. 하나의 메서드로 여러 조회 조건을 처리할 수 있어 호출부의 코드가 단순해집니다.

NotionClient(*, timeout_ms=60_000, query_policy=None)
get_database_rows(data_source_id, date_column=None, started_at=None, ended_at=None)
create_database(parent_page_id, title, properties, is_inline=False)
  • get_database_rows(data_source_id)만 호출하면 전체 행을, 날짜 인자를 함께 전달하면 해당 기간의 행만 조회합니다. 날짜 조건을 전달하면서 date_column을 생략한 경우에는 ValueError로 잘못된 호출을 차단합니다.
  • NotionClient()는 기본 타임아웃으로 동작하고, 웹 조회처럼 요청 간격 관리가 필요한 경우에만 query_policy를 전달합니다. 키워드 전용 인자(*)로 지정하여 인자 순서 혼동을 방지했습니다.

08주요 기능 ③ 취약도 분석

요약공지와 서비스 패키지를 패키지명 · 생태계 · 버전 기준으로 대조합니다. 버전 규칙은 생태계마다 상이하므로 pip, npm, Maven 등 13개 생태계별 비교 규칙을 적용하며, 비교할 수 없는 경우는 안전으로 간주하지 않고 "알 수 없음(unknown)"으로 분류합니다.

판정 예시

공지의 취약 범위가 >= 1.0, < 2.0이고 서비스가 동일 생태계 · 동일 패키지의 1.5 버전을 사용하는 경우, 쉼표로 연결된 조건을 모두 충족하므로 취약으로 판정하고 해당 공지의 심각도를 저장합니다. 2.1 버전은 범위를 벗어나므로 불일치로 처리됩니다.

생태계별 버전 비교

생태계비교 방식
pip (PyPI)packaging의 PEP 440 규칙
npm · Go · Rust · Erlang · GitHub Actions · Swiftsemver 규칙 (v 접두사 및 Go pseudo-version 지원)
NuGet · Maven · RubyGemsunivers 전용 비교기 (Maven Final · GA · RELEASE 별칭 포함)
Composerdev < alpha < beta < RC < stable < patch 순서
Pub빌드 식별자까지 비교하는 Pub 고유 규칙
other · 미등록숫자 · 점 또는 SemVer 표기만 비교하며, 그 외는 판정 불가

지원 조건 기호: < <= > >= = == != ≤ ≥ ≠. ||, 와일드카드, ^, ~ 표기와 임의 태그 · 커밋 해시는 판정 불가로 분류합니다. PyPI/pip, Cargo/rust 등 생태계 별칭은 정규화 후 비교합니다.

저장 규칙

상황저장 값
복수 취약점 일치최고 심각도 1건 (critical > high > medium > low)
동일 패키지의 버전 비교 불가확인된 취약점이 없는 경우 unknown (알 수 없음)
확인된 취약점 + 판정 불가 공지확인된 최고 심각도 유지
기존 unknown 패키지가 전체 분석에서 모두 비교 가능 · 불일치safe로 갱신하여 판정 불가 해소
그 외 불일치 · 관련 공지 없음기존 취약 판정을 자동 해제하지 않음
  • 패키지별 결과를 1회만 저장하여 Notion 요청 수를 최소화합니다.
  • 분석 실행 중에는 실행 버튼이 비활성화되며, 중복 실행 요청은 HTTP 409로 차단합니다.
구현 포인트 · 생태계별 버전 규칙 대응
  1. 초기 기준 — 가장 널리 사용되는 버전 관리 규칙인 SemVer를 기준으로 기본 버전 비교 규칙을 정의했습니다.
  2. 문제 발생 — 패키지 생태계마다 자체 버전 관리 규칙이 있어 SemVer 기준으로는 비교할 수 없는 버전이 존재했고, 이로 인해 판정 결측값이 발생했습니다. 예를 들어 PHP 생태계(Composer)는 dev · alpha · beta · stable 등 문자열 단계 간의 순서 규칙을 사용합니다.
  3. 1차 대응 — 결측값을 안전으로 간주하지 않고 unknown(알 수 없음) 태그로 분류하여, 판정 누락이 결과에 드러나도록 처리했습니다.
  4. 2차 대응 — 문제가 발생한 생태계의 공식 문서를 확인하여 버전 관리 규칙을 파악하고, 생태계별로 비교 로직을 분기 처리하여 결측값을 해소했습니다. 이후 전체 분석에서 비교가 가능해진 기존 unknown 패키지는 safe로 자동 갱신됩니다.

09주요 기능 ④ 시각화

요약화면은 업무 흐름에 따라 요약 → 수집 → 통계 → 매핑 분석 → 결과 → 근거 순으로 구성되어 있습니다. 차트는 외부 라이브러리 없이 HTML과 CSS로 구현했습니다.

아래 순서는 시연 순서와 동일하며, 각 링크는 새 탭으로 열립니다.

  1. 대시보드주요 기능을 한곳에 모아둔 메인 화면입니다. 저장된 공지 수, 관리 서비스, 패키지 현황과 공지 통계를 확인할 수 있으며, 신규 공지 가져오기로 수집을 실행하면 수집 · 중복 확인 · 저장 단계와 처리 건수가 실시간으로 표시됩니다.
  2. 보안 공지저장된 공지별 패키지, 취약 버전 범위, 게시일 · 갱신일, GitHub 원문 링크를 조회할 수 있습니다.
  3. 공지 분석수집한 공지 데이터의 분포를 분석하는 화면입니다. 심각도 분포, 생태계별 공지 수, 게시 추이, 공지 다발 패키지 상위 10개를 기간별로 확인할 수 있으며, 기간에 따라 일별 · 월별 · 연도별 단위가 자동 적용됩니다.
  4. 실행 상태저장된 공지를 서비스 패키지와 매핑하는 분석을 실행하고, 매핑 결과를 확인하는 화면입니다. 조회 → 판정 → 저장 단계와 함께 검사 패키지 · 취약점 일치 · 영향 패키지 · 판정 불가 건수가 표시되며, 최근 20건의 실행 이력이 기록됩니다.
  5. 분석 결과표시되는 취약도는 서비스 패키지에 저장된 취약도입니다. 패키지가 공지(advisories)의 취약 범위에 해당하는 경우 해당 공지의 심각도가 반영되어 노출됩니다. 서비스 · 심각도 · 검색어(패키지명, 서비스명, 비즈니스 도메인 등) 조건으로 조회할 수 있으며 50건 단위로 표시됩니다. 예: high 조회
  6. 취약 근거분석 결과 화면에서 확인한 취약점의 상세 정보를 확인하는 화면입니다. 패키지 토글을 펼치면 상단에 서비스에서 사용 중인 설치 버전이 표시되고, 토글 내부 표의 취약 범위와 비교하여 해당 패키지가 취약 범위에 포함되는지 확인할 수 있습니다. 판정 불가 사유, 현재 비교 결과와 저장값의 차이, 서비스별 위험 순위도 제공하며, 읽기 전용 화면으로 Notion 데이터를 변경하지 않습니다.

시연 시 참고: 최초 조회 화면은 Notion 조회로 인해 지연될 수 있습니다. 시연 전 각 화면을 한 번씩 조회해 두면 60초간 캐시 데이터로 즉시 표시됩니다.

구현 포인트 · 취약 근거 판정 방식
  • 취약 근거 화면은 분석 단계(processor.py)와 동일한 비교 함수(version_matches_range)를 재사용하여, 분석 결과와 근거 화면의 판정 기준이 어긋나지 않도록 했습니다.
  • 패키지별로 대조된 공지를 일치 공지와 비교 불가 공지로 구분하고, 일치 공지 중 최고 심각도로 판정합니다.
  • 이 판정을 Notion에 저장된 취약도와 비교하여, 값이 다른 패키지는 "저장값과 다름"으로 표시합니다. 새 공지 수집 후 재분석이 필요한 패키지를 찾을 때 활용할 수 있습니다.

10주요 기능 ⑤ 안정성 · 알림

요약GitHub, Notion, Slack 등 외부 서비스에 의존하므로 장애 상황에서의 안정적인 처리를 중점적으로 고려했습니다. 일시적 오류는 재시도하고, 실패와 빈 결과를 구분하며, 동일 오류는 1회만 알림을 전송합니다.

대상처리 방식
GitHub 요청서버 · 네트워크 오류는 최대 3회 재시도하며, 400 · 401 · 403 · 404는 연동 정보 확인이 필요하므로 즉시 중단합니다. 재시도 중에는 로그만 기록하고 최종 실패 시에만 알림을 전송합니다.
Notion 요청요청 간격을 0.5초 이상으로 유지하고, 429 · 5xx · 타임아웃은 최대 3회 재시도합니다(Retry-After 준수). 일부 건 저장에 실패해도 나머지는 계속 처리합니다.
화면 조회60초 캐시를 적용하고, 갱신 실패 시 마지막 정상 데이터를 표시합니다. 빈 데이터와 조회 실패를 구분하며 샘플 데이터로 대체하지 않습니다.
작업 실행수집 · 분석은 백그라운드로 실행되며, 동일 작업의 중복 실행을 차단합니다(409).

Slack 알림

구분전송 내용
공지 수집 · Notion 적재 완료[작업] 보안 공지 Notion 적재 — 기간, 수집 · 생성 · 수정 · 제외 · 실패 건수, 실패 사유(최대 5건)
취약도 분석 완료[작업] 취약도 분석 — 분석 범위, 공지 · 검사 패키지 · 취약점 일치 · 영향 패키지 · 알 수 없음 · 판정 불가 해소 건수
작업 오류GitHub 최종 수집 실패, Notion 연결 · 조회 · 저장 실패, 설정 로딩 오류
웹 · 서버 오류미처리 예외, HTTP 5xx, 백그라운드 작업 예외
  • 동일 예외가 여러 계층을 거치더라도 알림은 1회만 전송됩니다.
  • 토큰 · 웹훅 등 비밀 값은 마스킹 처리하고, < > &는 이스케이프하여 멘션으로 해석되지 않도록 합니다.
  • Slack 전송 실패는 수집 · 분석 결과에 영향을 주지 않습니다.
구현 포인트 · 비밀 값 마스킹 순서
  • 환경변수 중 이름에 TOKEN · SECRET · PASSWORD · WEBHOOK이 포함되거나 _KEY로 끝나는 값을 비밀 값으로 수집합니다.
  • 비밀 값을 길이 기준 내림차순으로 정렬한 뒤 순서대로 치환합니다. 짧은 비밀 값을 먼저 치환하면, 그 값을 포함하는 긴 비밀 값이 중간에 깨져 나머지 부분이 마스킹되지 않고 노출될 수 있기 때문입니다.
  • 긴 비밀 값부터 마스킹하여 이러한 부작용 없이 모든 비밀 값이 [REDACTED]로 처리되도록 했습니다.

python -B -m unittest discover -s tests -v

외부 서비스를 모의 처리하므로 실제 Slack 메시지나 Notion 데이터는 생성되지 않습니다.

브랜치 작업 순서

git switch -c feature/my-work            # 1. 개인 브랜치 생성 (최초 1회)
git add . && git commit -m "작업 내용"     # 2. 커밋
git push -u origin feature/my-work
git switch main && git pull origin main  # 3. 최신 main 반영
git switch feature/my-work && git merge main
git switch main && git merge feature/my-work && git push origin main   # 4. main 병합

충돌 발생 시 공동 작업자의 코드를 임의로 삭제하지 않고 담당자와 확인합니다.
